# Документация по безопасности API и валидации контрактов

В данном микросервисе реализован комплекс мер по обеспечению безопасности транспортного слоя, валидации входящего трафика и предотвращению утечки конфиденциальных данных.

## 1. CORS (Cross-Origin Resource Sharing)
* **Класс конфигурации:** `OpenApiValidationConfig` (бин `corsFilter`)
* **Приоритет в цепочке фильтров:** `Integer.MIN_VALUE` (Максимальный приоритет).
* **Описание:** Настроен перехват и обработка предварительных (Preflight) запросов `OPTIONS` от браузеров до их попадания в защищенные контексты безопасности и парсеры. Разрешен доступ для фронтенд-приложений из доверенных источников (конфигурируется через переменные окружения). Передача учетных данных (`AllowCredentials`) активирована.

## 2. Ограничение размера тела запроса (Защита от DOS/OutOfMemory)
* **Класс фильтра:** `CustomOpenApiValidationFilter` (наследник `OpenApiValidationFilter`)
* **Приоритет в цепочке фильтров:** `Integer.MIN_VALUE + 1` (срабатывает строго после CORS).
* **Описание:**
    * Для всех запросов по маске `/api/*` проверяется тип контента. Если заголовок `Content-Type` содержит `application/json`, фильтр сверяет HTTP-заголовок `Content-Length` с максимально допустимым лимитом.
    * Лимит задается в человекочитаемом формате (например, `2MB`) в конфигурационном файле через параметр `app.openapi.max-body-size` и парсится утилитой `DataSize`.
    * При превышении лимита запрос блокируется до выкачивания тела в память и выбрасывается `MaxUploadSizeExceededException` (HTTP Status `413 Payload Too Large`).

## 3. Строгая валидация по OpenAPI-контракту
* **Класс интерцептора:** `OpenApiValidationInterceptor`
* **Точка интеграции:** Spring MVC `InterceptorRegistry` для путей `/api/**`.
* **Описание:** Каждый входящий запрос проверяется на строгое соответствие спецификации OpenAPI (`openapi.yaml`). В случае обнаружения пропущенных обязательных полей, неверных типов данных или некорректных форматов (например, неверный формат даты), запрос принудительно прерывается.

## 4. Защита от утечки секретов и токенов в логи (Data Masking)
* **Класс обработчика:** `SafeValidationReportHandler` (внутри `OpenApiValidationConfig`)
* **Принцип работы:**
  При нарушении контракта валидатор Atlassian генерирует текстовый отчет об ошибке, в который могут попасть сырые конфиденциальные данные пользователя. Наш обработчик перехватывает этот отчет *в оперативной памяти до этапа записи в логгер* и производит двухэтапную очистку:
    1. **Токены авторизации:** Строки, содержащие `Bearer <token>` или `Basic <token>`, маскируются с помощью регулярных выражений и приводятся к безопасному виду `Bearer *******` / `Basic *******`.
    2. **JSON-поля тела запроса:** С помощью регистронезависимого паттерна `FIELD_PATTERN` сканируются упоминания критических полей (`password`, `secret`, `token`, `cookie`). Их значения точечно вырезаются и заменяются на `*******`.

В системные логи приложения (`log.error` / `log.warn`) поступает исключительно очищенный текст, что исключает утечку секретов в системы сбора логов (ELK / Grafana Loki).

## 5. Единый формат ошибок (Unified Error Response)
* **Класс исключения:** `CustomInvalidRequestException` (наследник `InvalidRequestException`)
* **Класс обработчика:** `GlobalExceptionHandler` (`@RestControllerAdvice`)
* **Описание:**
  После маскирования данных `SafeValidationReportHandler` формирует список безопасных строк ошибок и выбрасывает `CustomInvalidRequestException`. Глобальный обработчик перехватывает его и сериализует с помощью Jackson в стандартизированный JSON-ответ `ApiErrorResponse` для клиента:
  ```json
  {
      "status": 400,
      "error": "Bad Request",
      "message": "Schema request validation failed",
      "details": [
          "String \"Bearer *******\" is too short (length: 37, required minimum: 50)"
      ],
      "timestamp": "2026-05-21T15:25:05.126669900"
  }
  ```
  Это гарантирует, что даже в HTTP-ответах клиенту сырые секреты заменены звездочками.

## Ручное тестирование (Postman)

Для проверки механизмов валидации, лимитов body и маскирования токенов в репозиторий добавлена готовая тестовая коллекция.

* **Путь к файлу:** `src/test/resources/postman/Room-Booking.OpenApiTest.json`

### Инструкция по запуску:
1. Запустите приложение локально (профиль `local`).
2. Откройте Postman, нажмите кнопку **Import** в левом верхнем углу и выберите этот файл.
3. В импортированной коллекции вы найдете 4 запроса к демо-эндпоинтам:
- **GetRooms** — GET-запрос для проверки маскирования секретных полей.
- **PostBookingValid** — POST валидный запрос для проверки работы эндпоинта.
- **PostBookingNotValid** — POST невалидный запрос для проверки валидации по OpenAPI-спецификации при некорректных полях тела запроса.
- **PostBookingClearBody** — POST невалидный запрос для проверки работы по OpenAPI-спецификации при пустом теле запроса.
